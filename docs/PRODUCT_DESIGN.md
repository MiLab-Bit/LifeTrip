# LifeTrip 产品设计方案

> 版本：2026-08 v2 · 仓库：MiLab-Bit/LifeTrip  
> 参考：[KORA Agent 升级提案](./reference/kora_proposal_agent_upgrade.md)（Freya）— 从 Conversation 到 Task Completion

---

## 〇、竞争单位的切换

| 阶段 | 竞争单位 | LifeTrip 含义 |
|---|---|---|
| **以前** | 一次对话 / 一次推荐回答得多好 | 「给你几个店、写段攻略」 |
| **接下来** | 用户说了一件事，能不能**替他办成** | 「今晚这条 city walk **真的走完了**」 |

对于 LifeTrip，**回答只是开始，办成才是一次完整交互**：

```
以前：「安福路有什么好玩的？」→ 一串推荐
以后：「今晚想逛咖啡线。」→ 「线已生成」→ 「第 2 站已走到」→ 「下雨了，已换成室内站」→ 「今日走线完成」
```

用户不需要知道 Overpass、OSRM 是什么，只需要看到一个**持续推进的漫步 Agent**，而不是散落的 AI 回答。

---

## 一、一句话

**LifeTrip 是「地铁线路感」的 City Walk Agent：30 秒接下一个漫步任务，用地图和站牌替你规划、改线、走到终站。**

---

## 二、LifeTrip 现在在哪

### 2.1 已验证（L0）

| 维度 | 证据 |
|---|---|
| **形态成立** | Brief → 地图 polyline → 逐站 Walk UI 跑通 |
| **数据可接** | OSM POI + OSRM 步行，国内可 fallback fixture |
| **视觉差异** | 黑绿地铁美学，与攻略/文旅 App 区隔 |

### 2.2 下一阶段真正缺的（对齐 KORA 2.2）

| 缺口 | 现况 |
|---|---|
| **没有持续承接用户** | 无 Memory，每次从零选 vibe |
| **没有承接任务** | 能「生成线路」，不能「陪你走完并改线」 |
| **没有承接变化** | 下雨、闭店、走不动 — 不会自动推进 |

问题不是 LifeTrip 不够会推荐，而是**没有真正接住一条要走完的线**。

---

## 三、目标用户与定位

**核心用户：** 22–35 岁城里年轻人 — 下班/周末想出门，要**气质对的路**，不要文旅题。

| 维度 | LifeTrip | 攻略/地图 |
|---|---|---|
| 交付物 | **一条走完的 Line** | 散点或 A→B |
| 交互 | 地铁线/站码/换乘 | 列表或转向 |
| 叙事 | 当下逛法 | 典故/榜单 |

**不做什么：** 馆藏文献、票务支付（v1）、Foreign tourist 全品类 Travel OS。

## 四、KORA 案例 → LifeTrip 映射

### 案例 A：豫园订票 → **安福咖啡线**

| KORA 目标态 | LifeTrip 目标态 |
|---|---|
| 「我想去豫园」→ 票已订好 | 「今晚想逛咖啡」→ **线已生成，已加入今晚行程** |
| 暴雨 → 自动改下午行程 | 降雨 → **户外站换室内/缩短，一键确认** |
| 用户不知背后流程 | 用户只见「已替你改到 2 号站：某某书店」 |

### 案例 B：暴雨改行程 → **Walk 主动推进**

> 「你接下来两站都是户外，14:00–18:00 降雨较大。我把第 3 站换成室内古着店，步行少 8 分钟。需要我调整吗？」

不是天气推送，是**找出受影响的站 + 给出可执行改线 + 一键应用**。

### 案例 C：航班延误 → **Walk 会话中断恢复**

用户昨天规划了「周六 15:00 愚园线」但没去。今天打开：

> 「你昨天排了愚园咖啡线（3 站），要继续从第 1 站开始，还是重新选线？」

## 五、六个问题 → LifeTrip 五系统 + 验证

KORA 框架：一件事交出去，要连续回答六个问题。LifeTrip 同构如下：

| # | 问题 | LifeTrip 系统 | v1 范围 |
|---|---|---|---|
| 1 | 它到底要什么 | **理解 Intent** | 问题 vs 任务；「推荐店」vs「帮我走一条线」 |
| 2 | 我需不需要记住 | **记忆 Memory** | 偏好、未完成线路、走过哪几条 |
| 3 | 下一步怎么安排 | **规划 Plan** | 三轴选站 + 时间线 + 冲突检测 |
| 4 | 能不能替他做 | **执行 Execute** | 生成线、改线、跳过站（见权限分级） |
| 5 | 做完是不是真的成功 | **验证 Verify** | POI 可达、polyline 有效、店仍营业 |
| 6 | 中间发生变化怎么办 | **持续推进 Proactive** | 天气、闭店、用户停走 |

```
用户 ──▶ 理解 ──▶ 记住 ──▶ 规划 ──▶ 执行 ──▶ 验证
                              ▲                    │
                              └── 持续推进 ◀───────┘
```

## 六、五大系统（LifeTrip 版）

### 6.1 理解系统 · Intent

- **问题**：「安福路有什么 bar？」→ 回答即可，不进入任务
- **任务**：「帮我排今晚夜行线 / 走 coffee 线」→ 进入 **WalkTask** 生命周期
- 输出：`TaskEnvelope { type: "plan_walk" | "adjust_walk" | "resume_walk", ... }`

### 6.2 记忆系统 · Memory

> KORA：旅行档案。LifeTrip：**漫步档案**（轻量，先任务相关）

| 字段 | 示例 |
|---|---|
| 偏好 | vibe 权重、pace、常逛片区 |
| 进行中 | `walk_task_id`、当前站序、未完成原因 |
| 历史 | 走完的 lineCode、日期、时长 |
| 摘要 | 「上次提到想逛巨富古着，未生成」 |

用户感受：第二次打开不说「我是慢逛型」，LifeTrip 说「继续上周未走完的 L-V3？」

**L1 只做任务记忆，不做完整画像**（对齐 KORA 12.3）。

### 6.3 规划系统 · Plan

- 输入：Memory + POI 层（OSM + curated + 可选高德标签）
- 输出：**线性 WalkTimeline**（非点状推荐）
- 检测：站间过长、营业冲突、时长超标、天气不适合户外

### 6.4 执行系统 · Execute + 权限 L0–L3

| 级别 | LifeTrip 操作 | 确认 |
|---|---|---|
| **L0** | 查 POI、查天气、算路线 | 否 |
| **L1** | 生成/更新线路草稿、加入「今晚行程」 | 否 |
| **L2** | 跳过站、替换站、应用改线 | **一次确认** |
| **L3** | 第三方预约、支付、删账号 | 强制确认（v2+ 再做） |

失败分流（对齐 KORA）：

| 失败类型 | 处理 |
|---|---|
| Overpass 超时 | 重试 → cache → fixture |
| 店已关 | 换同 vibe 备选站 |
| 用户拒绝改线 | 标记任务暂停 |
| 支付失败（未来） | 立即停止 |

### 6.5 验证系统 · Verify

- 几何：OSRM 是否返回有效 polyline
- POI：`source` + `verified_at` 是否存在
- 走线：用户是否到达终站 / 主动标记完成
- 标注：**绿标** curated 核实 · **蓝标** OSM · **灰标** 未核实

### 6.6 质量系统 · Eval Harness

> KORA：题库不是 FAQ，是回归测试集。LifeTrip 同构三层：

| 层级 | 内容 | 标准 |
|---|---|---|
| **事实题** | POI 坐标、营业、站名 | 知识版本内 **100%** |
| **决策题** | 三轴选站、雨天改线是否合理 | 人工 + rubric 抽检 |
| **应急题** | 闭馆、暴雨、POI 不存在 | 答错后果大，优先 50 道 |

每次改 planner / prompt / POI 库 → 自动跑核心题库（L3 引入）。

### 6.7 主动推进 · Proactive

触发器（LifeTrip 版）：

| 事件 | 行动 |
|---|---|
| 降雨预报 | 提议室内替换站 |
| 用户 24h 未继续未完成任务 | 提醒一次（可关） |
| 常走片区有新 curated 站 | 「L-C2 新增一站，要并入吗？」 |
| 用户在站附近停留 >30min | 「要跳过下一站直接喝咖啡吗？」 |

判断链：发生了什么 → 影不影响当前 WalkTask → 多大 → 是否告知 → **一键操作是什么**

## 七、Wedge 策略（学习 KORA 第一 wedge = 门票）

**KORA：** 先只做「豫园门票」闭环，再横向复制。

**LifeTrip：** 先只做 **一条 WalkTask 闭环**：

> 用户：「今晚安福，咖啡，90 分钟，慢逛。」  
> LifeTrip：理解 → 规划 → 生成 L-C2 → 用户开走 → 可 skip 一站 → 走到终站 → 验证完成。

**为什么选它：**

- 高频（本地年轻人周末/下班）
- 结果可验证（polyline + 站序 + 完成态）
- 无需支付/票务合规
- 失败可人工 fallback curated 线

**跑通后再复制：**

- 夜行 / 古着 / 画廊 vibe
- 主动天气改线
- Memory 跨天 resume
- 小程序 / 语音「下一站换室内」

## 八、核心 KPI

> KORA：**任务完成率**。LifeTrip 对齐为：

### 主指标 · 走线任务完成率

```
WalkTask 完成率 = 被识别为「走线任务」的需求中，最终验证「走到终站或用户确认完成」的比例
```

- 不计：用户主动取消、需求变更
- 拆分：**任务理解率** · **规划成功率** · **验证通过率** · **改线成功率** · **人工介入率**

辅助：Brief→开走转化、平均 walk 时长、二刷率。

对话/生成次数只是流量指标，**不是 L1+ 的优化目标**。

## 九、数据层（见 DATA_SOURCES.md）

- **主：** OSM Overpass + OSRM
- **加权：** curated 编辑精选
- **可选：** 高德 POI 标签（「外语友好」类结构化标签，不存原始评论）
- **不采用：** 馆藏 API、评论爬虫

更新策略：营业状态高频；评分标签低频。

## 十、技术分层路线图

| 层 | 交付 | 对应 KORA 月 |
|---|---|---|
| **L0** ✅ | 规划 + 地图 + 规则文案 | 周 0：人工能走通一条线 |
| **L1** | curated + cache + WalkTask 模型 | 周 1：机器生成稳定 |
| **L2** | Memory + skip/reroll + 权限 L0–L2 | 周 2–3：跨时间 continue |
| **L3** | Eval Harness + LLM 润色 + 来源标注 | 周 4：50–100 真实 walk 复盘 |
| **L4** | Proactive 天气 + 小程序 | 第二月：设定完成率基线 |

### 第一个月只验证一个闭环（对齐 KORA §12）

**问题：** 真实用户把「今晚安福咖啡慢逛 90 分钟」交给 LifeTrip，能否从理解走到验证完成？

| 周 | 目标 |
|---|---|
| **W1** | 人工用 OSM+curated 走通全链路；定义成功/失败 |
| **W2** | Agent 接手：意图识别、规划、返回 polyline；L0–L2 权限 |
| **W3** | 任务 Memory + 未完成提醒（只做任务相关字段） |
| **W4** | 50–100 次真实 walk；复盘失败：理解/规划/验证/用户未确认 |

成功标准：**任务能识别 · 链路能跑通 · 失败能识别并降级** — 再设完成率目标。

## 十三、工程下一步

1. **L1** `content/curated/` + planner 加权 + POI cache  
2. **L2** `WalkTask` 实体 + `POST /v1/walks/{id}/skip` + Memory SQLite  
3. **L3** `packages/contracts` + Eval 50 题 + 来源绿/蓝/灰标  
4. **L4** 天气 trigger → 改线提案 API  

代码入口：`apps/api/app/planner.py` → 演进为 `plan/` + `walk/` 模块。

## 十四、最后一句（改自 KORA §13）

**不要先做一个 City Walk Agent 平台。先证明 LifeTrip 能替一个真实用户，把一条真实的漫步任务办完。**

这件事成立，Memory、Proactive、Eval、多城复制都只是规模化问题。
