# LifeTrip 产品升级方案 · v0.5 → v0.7

> 日期：2026-10-15 · 基于 v0.4.0 现状 + 全球竞品调研 + 中国文旅市场数据

---

## 〇、现状诊断

### 已验证能力（v0.4.0）

| 系统 | 代码量 | 完成度 |
|---|---|---|
| WalkTask 全生命周期 | walk/service.py 162行 + temporal workflows | ✅ 闭环 |
| 路线规划 | plan/planner.py 234行 | ✅ 三轴选站 |
| 任务记忆 | memory/store.py 188行 SQLite | ✅ 任务级 |
| 叙事润色 | narrative/polish.py 183行 | ✅ 静态文案 |
| 意图识别 | intent.py **47行** | ⚠️ 偏薄 |
| 验证系统 | verify.py + 标注体系 | ✅ 绿/蓝/灰标 |
| Eval 50题 | eval/harness.py 137行 | ✅ 回归 |
| 天气改线 | proactive/weather.py | ✅ 雏形 |
| 9条 curated 线 | content/curated/ | ✅ 3片区 |
| PWA 前端 | React + MapLibre | ✅ 可用 |

### 核心矛盾

**LifeTrip 已证明能帮用户「走完一条线」，但还没证明用户「愿意回来走第二条」。**

v0.4 解决了「一次任务闭环」；v0.5+ 要解决「持续留存 → 口碑传播 → 规模增长」。

```
v0.4 (现状)     v0.5                v0.6              v0.7
走完一条线  →  值得回来走      →  愿意分享出去    →  全天候全场景
                  ↑ 留存              ↑ 增长            ↑ 规模
```

| 版本 | 主题 | 核心指标 | 周期 |
|---|---|---|---|
| **v0.5** | 值得回来 | 二刷率（D7/D14 回归） | 4-6 周 |
| **v0.6** | 愿意分享 | 分享率 + 新客 CAC | 4-6 周 |
| **v0.7** | 全天候 | DAU + 时段覆盖 | 6-8 周 |

## 二、v0.5 — 值得回来

> **目标：从「任务记忆」升级到「用户关系」。第二次打开，LifeTrip 认识你。**

### 2.1 WalkDNA 用户画像

**要解决什么：** 当前 Memory 只有任务级记忆（走没走完、当前站序），没有用户偏好学习。用户每次回来都要重新说「我是慢逛型」。

**做什么：**

| 子系统 | 现状 | v0.5 交付 |
|---|---|---|
| 偏好采集 | 手动 brief 输入 | 从已完成 WalkTask 自动提炼 |
| 用户画像 | 无 | WalkDNA：pace / vibe / 片区 / 时段 / 季节偏好 |
| 主动推荐 | 无 | 第二次打开主动推送「上次安福咖啡没走完，继续？」 |
| 冷启动 | 每次从零 | 首次走完后生成 WalkDNA 初始版 |

**技术方案：**

```
memory/store.py (188行)
  ↓ 扩展
WalkProfile 表：
  - user_id, vibe_weights JSON, pace_preference,
    frequent_districts[], preferred_time_slots[],
    completed_walks_count, total_walk_duration
  ↓ 自动更新触发器
每次 WalkTask 完成后 → 提炼偏好 → upsert WalkProfile
```

**工作量：** ~2 周（扩 memory 表 + 偏好提炼逻辑 + 前端展示）

### 2.2 叙事引擎 v2 — 到站讲故事

**要解决什么：** 当前 narrative 是静态文案（走之前看一眼），不是行进中的陪伴。竞品（City's Voice / RouteStory / TalkieWalkie）都在做 location-triggered 讲述。

**做什么：**

```
到达站点 (GPS proximity trigger)
  ↓
推送站牌叙事（分层可选）
  ├── L1 快速版：1 句话（15 秒扫一眼）
  ├── L2 标准版：3-4 句（60 秒，默认）
  └── L3 深度版：文化/历史/建筑延伸（可选展开）
  ↓
置信度标注（已有绿/蓝/灰标体系，直接复用）
```

**关键设计决策：**

- **不做 TTS 音频**（v0.5 范围）—— 先验证用户是否看文字叙事；音频留到 v0.7
- **分层叙事**参考竞品最佳实践：City's Voice 的「历史/建筑/轶事」分层 + RouteStory 的「60秒法则」
- **触发机制**：GPS proximity（到站 50m 内）+ 用户点击站牌 marker 双触发，避免误触

**技术方案：**

```
narrative/polish.py (183行)
  ↓ 扩展
新增 narrative/layers.py：
  - generate_layered(poi_id, user_walk_dna) → {quick, standard, deep}
  - 每层独立 prompt，共享 POI 知识库 context
  
前端新增：
  - 到站弹窗组件（取代当前的静态站牌）
  - 用户可选择叙事深度
```

**工作量：** ~2 周（分层叙事 prompt + 前端弹窗 + proximity 触发）

### 2.3 轻量游戏化 — 探索图谱

**要解决什么：** 走完一条线后没有「留下来」的理由。竞品（Walksy / Walkable）证明探索进度可视化是最强的回归驱动。

**做什么：**

| 功能 | 描述 | 参考竞品 |
|---|---|---|
| **片区点亮** | 走完一条线后，地图上该片区从暗变亮 | Walkable 热力图 |
| **站牌收集册** | 走过的每个 POI 记入收集册，显示总数和覆盖率 | Walksy 地标收集 |
| **步行徽章** | 「咖啡达人」走完3条咖啡线；「夜行人」走完夜行线；「全勤」连续4周 | Walksy 成就系统 |
| **Walk 数据** | 总公里数、总站点数、走过片区数（一个数字，大而醒目） | 小红书「200万公里」叙事 |

**关键设计决策：**

- **不做迷雾地图**（太重，偏离地铁美学）—— 做「点亮」而非「揭开」
- **不做排行榜/领地**（v0.5 不引入社交竞争）—— 留到 v0.6
- **徽章是装饰性的**，不与功能绑定，纯情绪价值

**技术方案：**

```
新增 explore/ 模块：
  - explore/badges.py：徽章定义 + 触发判定
  - explore/coverage.py：片区覆盖率计算
  - explore/collection.py：POI 收集册
  
前端新增：
  - 探索图谱页面（个人主页）
  - 片段点亮效果（MapLibre layer 切换）
  - 徽章展示墙
```

**工作量：** ~2 周（后端 explore 模块 + 前端图谱页）

### 2.4 v0.5 工程量

| 模块 | 新增/改动 | 估时 |
|---|---|---|
| WalkDNA 用户画像 | memory 扩表 + 偏好提炼 | 2 周 |
| 叙事引擎 v2 | narrative/layers + 前端弹窗 | 2 周 |
| 探索图谱 | explore/ 模块 + 前端图谱页 | 2 周 |
| intent.py 加强 | 47行 → ~120行，补 intent 分类 | 0.5 周 |
| **合计** | | **~5-6 周** |

### 2.5 v0.5 成功标准

```
主指标：D7 二刷率 ≥ 30%
辅助指标：
  - WalkDNA 覆盖率（走完一次的用户有画像的比例）≥ 80%
  - 站牌叙事打开率 ≥ 50%
  - 探索图谱页面访问率 ≥ 40%（回访用户）
```

## 三、v0.6 — 愿意分享

> **目标：走完一条线，天然生成一张可分享的「地铁漫步卡」。**

### 3.1 Walk Card 导出

**核心洞察（来自文旅技能库）：** 增长飞轮的关键杠杆 = 让走完的路线**天然适合分享**。

**做什么：**

```
走完一条线
  ↓ 自动生成
Walk Card（竖版图文卡）
  ├── 地铁路线图缩略（黑绿地铁美学）
  ├── 站点打卡序列（✓ ✓ ✓ ✓ 终站）
  ├── Walk 数据：X 公里 · X 站 · X 分钟
  ├── 用户照片（如果有）
  └── LifeTrip 水印 + 二维码
  ↓
一键导出（保存图片 / 分享）
```

**技术方案：**

- 前端用 Canvas/SVG 生成卡片图片
- 可选：服务端 puppeteer 截图渲染（更精美但重）
- 建议 v0.6 先做前端 Canvas 版本

### 3.2 路线评价系统

**做什么：**

| 评价维度 | 输入方式 |
|---|---|
| 整线推荐度 | 1-5 星 |
| 单站评分 | 每个 POI 可标记「值 / 不值」 |
| 一句话感受 | 可选文字 |
| 照片上传 | 可选 |

评价数据回灌：
- 整线评分 → 影响 curated 线排序权重
- 单站评分 → 影响 planner 选站打分
- 评价成为「社区信号」，为 v0.7 社区 Feed 铺路

### 3.3 社区路线入口（MVP）

**做什么：**

- 用户走完一条非 curated 的自由线后，可以「发布这条线」
- 发布时自动填充：站点序列、时长、距离、WalkDNA 标签
- 社区 Feed 展示：最新发布 / 热门线路 / 同片区推荐
- 其他用户可「加入同款」→ 直接导入为自己的 WalkTask

**关键设计决策：**

- v0.6 只做**发布 + 浏览**，不做社交关注/评论
- 社区路线标注「用户生成」（蓝标/灰标），与 curated 绿标区分
- 降低发布门槛：走完即可发布，不需要额外写内容

### 3.4 v0.6 工程量

| 模块 | 估时 |
|---|---|
| Walk Card 生成 | 1.5 周 |
| 路线评价系统 | 1.5 周 |
| 社区路线 MVP | 2 周 |
| **合计** | **~5 周** |

### 3.5 v0.6 成功标准

```
主指标：Walk Card 分享率 ≥ 15%（走完的用户中）
辅助指标：
  - 社区路线发布数 ≥ 50 条/月
  - 社区路线导入转化率 ≥ 20%
  - 卡片带来的新客占比 ≥ 10%
```

## 四、v0.7 — 全天候全场景

> **目标：从「下班走一条」扩展到「全天任何场景」。**

### 4.1 夜行模式

**市场依据（来自文旅技能库）：** 2025 年「日落到深夜」是文旅第一大趋势，夜经济话题持续增长。

**做什么：**

| 子功能 | 描述 |
|---|---|
| 夜行 LineCode | L-N 系列线路（Neon）：日落点 → 夜市 → 灯光 → 深夜食堂 |
| 夜间安全标注 | 每个夜行站标注：照明（亮/暗）、人流（密/疏）、治安（绿/黄） |
| 日落触发 | 黄昏时主动推送：「今天日落 17:32，要不要走一条夜行线？」 |
| 夜行徽章 | 「夜行人」徽章（与 v0.5 游戏化系统打通） |

### 4.2 音频导览

**做什么：**

- 到站自动播放 60 秒语音讲解（TTS）
- 基于叙事引擎 v2 的分层内容，音频版默认播 standard 层
- 耳机检测：插耳机后自动切换音频模式
- 后台播放：锁屏可继续听

**技术方案：**

- TTS 引擎：可用 CTYun 或 Edge TTS
- 音频缓存：首次走线时预生成，缓存到 IndexedDB
- 格式：Opus（体积小，PWA 友好）

### 4.3 高德 POI 标签增强

**做什么：**

- 高德 API 获取：营业状态、评分、标签（如「精品咖啡」「古着」「画廊」）
- Planner 加权：高德评分 > 4.5 的 POI 权重提升
- 实时验证：出发前检查沿途站点是否仍在营业
- 减少「到了发现关门」的失败率

### 4.4 多城扩展

**做什么：**

- 上海 → 北京 / 杭州 / 成都（步行友好度高的小城优先）
- 每城首批 5 条 curated 线
- WalkDNA 跨城迁移（用户的 pace/vibe 偏好跟人走）

### 4.5 v0.7 工程量

| 模块 | 估时 |
|---|---|
| 夜行模式 | 2 周 |
| 音频导览 | 3 周 |
| 高德 POI 标签 | 1.5 周 |
| 多城扩展（首批） | 2-3 周 |
| **合计** | **~8-10 周** |

## 七、优先级总结（执行顺序已定）

### 排序原则

1. **依赖关系优先**：被别人依赖的模块先做
2. **用户感知优先**：同样工程量，选用户更快看到的
3. **留存 > 增长 > 扩展**：先解决「回不回来」，再解决「拉不拉新」，最后扩场景

### 执行顺序

```
━━━ Sprint 1 (Week 1-2) ━━━━━━━━━━━━━━━━━━━
 ① WalkDNA 用户画像（后端）
    → 它是后续所有个性化的地基
    → 叙事引擎、社区推荐、多城迁移都依赖它
    → 纯后端，前端改动小，交付快

━━━ Sprint 2 (Week 3-4) ━━━━━━━━━━━━━━━━━━━
 ② 探索图谱（全栈）
    → 留存杠杆最大：片区点亮是最强「再打开」动机
    → 不依赖 WalkDNA，只需已完成 WalkTask 数据（已有）
    → 用户感知最快：走完立刻看到地图变化
    → 同期并行：intent.py 加固（0.5周，不挡主线）

━━━ Sprint 3 (Week 5-6) ━━━━━━━━━━━━━━━━━━━
 ③ 叙事引擎 v2（全栈）
    → 体验差异化，但工程量最重（prompt + 前端弹窗 + proximity 触发）
    → 放第三是因为：前两项解决「回不回来」，这项解决「回来好不好玩」
    → 排序可浮动：如果 Sprint 1-2 提前完成，这项提前

━━━ Sprint 4 (Week 7-8) ━━━━━━━━━━━━━━━━━━━
 ④ Walk Card 分享（前端为主）
    → 增长引擎，但依赖前面走得稳（用户愿意走才有东西可分享）
    → 工程量轻（Canvas 生图），ROI 极高

━━━ Sprint 5 (Week 9-12) ━━━━━━━━━━━━━━━━━━━
 ⑤ 路线评价 + 社区路线 MVP
    → UGC 飞轮启动器
    → 社区需要一定用户基数才有意义，排在增长之后

━━━ Sprint 6+ (Week 13+) ━━━━━━━━━━━━━━━━━━━
 ⑥ 夜行模式 → ⑦ 音频导览 → ⑧ 多城
    → 场景扩展，按市场需求紧迫度排序
    → 夜行优先：2025 年文旅第一大趋势，且能复用现有架构
    → 音频第二：依赖叙事引擎 v2 的分层内容
    → 多城最后：需要前 7 项都稳定后再规模化
```

### 为什么是这个顺序

| 决策点 | 选择 | 理由 |
|---|---|---|
| WalkDNA vs 探索图谱谁先 | **WalkDNA 先** | 它是地基，叙事/社区/多城都要用；探索图谱自包含不依赖它 |
| 探索图谱 vs 叙事引擎谁先 | **探索图谱先** | 留存杠杆更大（竞品验证探索可视化是最强回归动机），工程量更轻 |
| Walk Card vs 社区谁先 | **Walk Card 先** | 卡片分享零用户基数门槛，社区需要人才能转起来 |
| 夜行 vs 音频谁先 | **夜行先** | 市场趋势最热，复用现有线路生成逻辑；音频是锦上添花 |
| 音频 vs 多城谁先 | **音频先** | 音频提升单城体验上限，多城是规模化问题，验证未完成前不急 |

### 快速路径（如果只有 4 周）

只做 ①WalkDNA + ②探索图谱，上线 v0.5 MVP，验证二刷率。这是最小可行升级。

### 砍刀路径（如果资源紧张）

| 砍掉 | 影响 | 可接受条件 |
|---|---|---|
| 叙事引擎 v2 | 体验打折但不阻断 | 如果静态文案够用 |
| 社区路线 | 增长引擎延后 | 如果 Walk Card 分享够拉新 |
| 音频导览 | 体验降级 | 如果文字叙事够好 |
| 多城 | 规模化延后 | 上海没饱和前不急 |

## 八、风险与缓解

| 风险 | 概率 | 缓解 |
|---|---|---|
| WalkDNA 偏好提炼不准 | 中 | 首版只做显式偏好（用户走完后选标签），不做隐式推断 |
| 叙事内容质量不够 | 中 | 复用 curated 绿标内容作为 ground truth，LLM 只做语气翻译 |
| 游戏化做了但没人看 | 低 | 最小可行版（只做片区点亮 + 一个数字），不过度投入 |
| 社区路线质量参差 | 中 | 灰标标注 + 社区评分排序 + 举报机制 |
